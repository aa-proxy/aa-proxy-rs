Dynamic Overlay Builder — Help
REST, WebSocket and legacy topic integration

              

                
Getting started
                  
  1. Select Add field. Fields are blank by default.
  2. Choose a data type, label, source ID, field key, unit and fallback.
  3. Select Generate text → preview to update the local overlay text editor.
  4. Select Save overlay to write the existing overlay.json configuration.
  5. Send data from your OBD reader or other client; use Refresh received values to inspect it.

                  
Load OBD example explicitly inserts test-only values. Nothing is uploaded or saved until you choose a corresponding action.

                

                
Which field type should I choose?
                  
Dynamic REST / WS: New authenticated telemetry: {{ws.overlay.obd.rpm}}. Send data through POST /overlay/data or WS /ws/overlay.

                  
Existing WS topic: Preserve the old event bus, e.g. {{ws.obd.rpm}}. No new data token or migration is required.

                  
Static text: A label and fixed text, with no data connection.

                

                
Sample values vs live values
                  
Sample / test value is optional. Leave it empty when designing a real integration; it is not written as a live default. It appears in the preview only after you enter it, or when you explicitly load the OBD example.

                  
LIVE means a recent value was returned by GET /overlay/data. STALE means its TTL expired; the configured fallback is shown. The browser reports what it last refreshed, not a continuously connected telemetry feed. Legacy topics are not inspected by this REST endpoint.

                  
Generated integration examples use JSON null placeholders for fields without test values. Replace those with real sensor data; Send example REST update refuses to send empty test fields.

                

                
Partial updates and field-specific TTL
                  
Previously a second update for the same source replaced its entire values object. Sending just coolant_temp_c could remove an earlier rpm value.

                  
Now the new API merges fields. For example, send {"source":"obd","values":{"rpm":2500},"ttl_ms":3000}, then send {"source":"obd","values":{"coolant_temp_c":86},"ttl_ms":5000}. Both fields are available independently. Sending coolant again does not refresh RPM's clock.

                  
After 3 seconds without a new RPM update, RPM falls back while coolant can remain valid for up to 5 seconds from its own last update. Sending JSON null for a field explicitly makes the overlay use its fallback.

                

                
REST / WebSocket and security
                  
Set the OVERLAY_DATA_TOKEN environment variable on the running proxy (minimum 16 characters) to enable the new API. Use Authorization: Bearer TOKEN for REST; WebSocket clients authenticate with an initial {"type":"auth","token":"TOKEN"} message.

                  
REST: POST /overlay/data writes values, and GET /overlay/data reads the current status. WebSocket: connect to /ws/overlay and send {"type":"update","source":"obd","values":{"rpm":2500},"ttl_ms":3000}.

                  
The integration examples under the Builder can be copied and adapted. Do not expose this plain-HTTP management service or token on untrusted networks.

                

                
Legacy scripts, persistence and limits
                  
Old scripts writing /dev/shm/overlay.json, existing {{ws.*}} placeholders, and /raw-topic-data are unchanged. The Builder writes the JSON only when you select Save overlay; REST/WS updates live only in RAM.

                  
Do not let a shell script and the Builder write the same overlay file concurrently: whichever writes last controls the layout. The default /dev/shm file is lost on reboot; use a persistent configured path for layouts that must survive restarts.

                  
Limits: 32 sources; 32 fields per source; 250–60,000 ms field TTL; 16 KiB per REST/WS message. The overlay renderer still handles the visual rendering.
